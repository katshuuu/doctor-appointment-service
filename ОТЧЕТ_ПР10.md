## 2. Цель работы

Цель практической работы — освоить административную панель Django
и углубить навыки работы с данными через Django ORM на примере
индивидуального сквозного проекта «Сервис записи к врачу».

Задачи работы:
1. зарегистрировать модели предметной области в Django Admin
   и настроить отображение, поиск, фильтрацию и связанные объекты;
2. проверить и доработать ORM-запросы списков, карточек, статистики
   и поиска свободных врачей;
3. заменить булев признак отмены записи на статусы `TextChoices`;
4. вынести повторяющиеся условия в менеджер и QuerySet;
5. открывать карточку врача по `slug` и формировать адрес методом
   `get_absolute_url()`;
6. передать общие данные в шаблоны через контекстный процессор;
7. реализовать вычисляемое поле `GeneratedField`;
8. проанализировать SQL-запросы с помощью Django Debug Toolbar;
9. актуализировать документацию и зафиксировать результат в Git.

Сущности учебного примера Roomly сопоставлены с проектом так:

## 4. Индивидуальный проект

**Название проекта:** Сервис записи к врачу

**Основные модели, доработанные на ПР10:**

- `Doctor` (`apps/doctors/models.py`) — поля `id`, `name`, `specialty`,
  уникальный `slug`; методы `save()` (транслитерация имени),
  `get_absolute_url()`.
- `Patient` (`apps/patients/models.py`) — поля `id`, `name`, `age`;
  вычисляемое поле `is_minor` (`GeneratedField`, `age < 18`).
- `Appointment` (`apps/appointments/models.py`) — поля `id`, `doctor`,
  `patient`, `appointment_date`, `appointment_time`, `status`
  (`TextChoices`: ACTIVE, CANCELLED, COMPLETED); метод `cancel()`;
  менеджер `AppointmentManager` на основе `AppointmentQuerySet`
  с методами `active()`, `cancelled()`, `completed()`, `for_date()`.

**Настройки административной панели:**

Модели врача, пациента и записи зарегистрированы через `@admin.register`.
Адрес панели: `/admin/`. У списков заданы `list_display`,
`list_display_links`, `search_fields`, `list_filter`, `ordering`.
Поиск записи идёт по имени врача и пациента (`doctor__name`,
`patient__name`), фильтр записи — по статусу, дате и врачу.
На карточках врача и пациента подключены `TabularInline` связанные
записи (`extra = 0`, `can_delete = False`). У врача включены
`view_on_site` и столбец ссылки на публичную страницу. Названия
приложений заданы через `AppConfig.verbose_name`. Создание записи
в Admin не заменяет проверку занятости слота на сайте.

**Изменения моделей, миграции и менеджер QuerySet:**

Поле `is_cancelled` заменено на `status`. Миграция схемы добавляет
поле со значением по умолчанию `active`; миграция данных
`0003_migrate_appointment_statuses` переносит `is_cancelled=True`
в `cancelled`, остальные записи — в `active`; затем старое поле
удаляется. Завершённый статус автоматически по дате не проставлялся:
в исходных данных его не было. Для врача добавлены `slug` (заполнение
существующих записей, затем уникальность) и формирование slug
при сохранении через Unidecode и `slugify`. Для пациента добавлен
`GeneratedField`. Учебное изменение длины имени — `max_length=250`.
Менеджер `Appointment.objects` сохраняет доступ ко всей истории:
`all()` включает отменённые записи, выборка по статусу идёт через
методы QuerySet. Методы менеджера используются в представлениях
списка записей, свободных врачей и статистики.

**Проверенные ORM-запросы, фильтрация, сортировка, пагинация
и статистика:**

Список записей строится одним QuerySet: `select_related`,
`annotate` с `F("doctor__name")` и `F("patient__name")`, фильтры
по дате (`for_date()`), врачу, пациенту и статусу, поиск через `Q`,
сортировка по белому списку `SORT_FIELDS`, `Paginator` по 5 записей.
Ссылки страниц сохраняют GET-параметры через `{% querystring %}`.
Карточка записи загружает врача, специальность и пациента
`select_related`. Статистика считает `total_bookings` и отдельные
`Count` с `filter=Q(status=...)` для ACTIVE, CANCELLED и COMPLETED,
а также группирует активные записи по врачам (`annotate` + `values`,
отбор групп `appointments_count__gt=1`). Неверная дата не уходит
в SQL: показывается сообщение «Укажите корректную дату.».
Отсутствие объекта обрабатывается `DoesNotExist` и ответом 404.

**Результаты проверки доступности врачей с учётом статусов:**

Свободный врач на дату определяется так: занятые идентификаторы
берёт `Appointment.objects.active().for_date(selected_date)`, затем
`Doctor.objects.exclude(pk__in=...)`. Отменённая и завершённая запись
дату не занимают. На дату `2026-09-15` Смирнова Анна Сергеевна
не показывается (есть активные записи), Петров Олег Викторович
показывается (запись 3 имеет статус CANCELLED). После смены статуса
в Admin список свободных врачей и статистика изменяются в соответствии
с правилом только ACTIVE.

**Результаты анализа SQL-запросов (Django Debug Toolbar):**

При `DEBUG = True` подключены `debug_toolbar`, middleware и маршрут
`__debug__/`. На списке записей основной SELECT содержит JOIN
связанных таблиц, условия фильтра и `ORDER BY`; пагинация даёт
`LIMIT` и отдельный `COUNT`; форма списка дополнительно читает
справочники врачей и пациентов. На карточке записи один запрос
с JOIN заменяет отдельные обращения к врачу и пациенту.
Признаки N+1 (запрос к связанному объекту на каждую строку страницы)
на этих сценариях не наблюдались. `prefetch_related()` для списка
записей не добавлялся: нужные связи уже закрывает `select_related`.

**Краткое описание выполненной доработки:**
Сохранены структура Django-проекта ПР9, страницы сайта и консольный
JSON-слой. Веб-интерфейс по-прежнему читает `db.sqlite3` через ORM,
исходная база ПР7 `data/doctor_appointment.sqlite` не изменялась.
Администрирование вынесено в Django Admin. Признак отмены стал
тремя статусами с переносом существующих 15 записей (12 ACTIVE,
3 CANCELLED с идентификаторами 3, 7 и 12). Карточка врача открывается
по адресу вида `/doctors/smirnova-anna-sergeevna-1/`. Контекстный
процессор `site_context` передаёт в шаблоны `site_name` и
`doctors_count`. README.md приведён в соответствие с текущей
реализацией. Учебные модели «Блогикума» в проект не переносились.

## 5. Результат работы

В результате выполнения ПР10:
- модели врача, пациента и записи зарегистрированы в Django Admin,
  настроены столбцы, поиск, фильтрация, сортировка и связанные записи
  через inline;
- созданы и применены миграции схемы и данных, в том числе переход
  с `is_cancelled` на `status`;
- менеджер и QuerySet записи используются в представлениях;
- список записей фильтруется, сортируется и разбивается на страницы
  с сохранением параметров;
- свободные врачи определяются по дате и статусу ACTIVE;
- статистика учитывает ACTIVE, CANCELLED и COMPLETED
  (15 / 12 / 3 / 0);
- подробная страница врача открывается по slug,
  `get_absolute_url()` формирует адрес именованного маршрута
  `doctors:detail`;
- контекстный процессор передаёт общие данные в шаблоны;
- `GeneratedField` `is_minor` формируется базой данных;
- SQL проверен через Django Debug Toolbar;
- `README.md` соответствует текущему состоянию проекта;
- результат зафиксирован в Git.

Ограничение: публичные формы создания записи по-прежнему не входят
в эту версию; Admin позволяет менять данные, но сам по себе не
проверяет конфликт времени приема. Скриншоты сценариев используются
при устной защите и не заменяют код, тесты и описание решений.
